# 鸿蒙跨平台框架 AI 诊断工作流 — Agent & Skill 测评方案及落地实践

> **参照腾讯 TEG《AI Agent & Skill 测评方案及落地实践》方法论，结合鸿蒙跨平台框架 AI 诊断工作流实际场景整理**

---

## 1. 背景：为什么要做测评？

### 1.1 诊断工作流的测评痛点

鸿蒙跨平台框架 AI 诊断工作流是一个多 Agent 协作系统（分类定界 → 信息采集 → 根因分析 → 修复建议 → 代码修改 → 报告沉淀），面临三大传统软件没有的问题：

| 痛点 | 表现 | 影响 |
|------|------|------|
| **非确定性** | 同一 Issue 多次诊断结果不同，"跑通一次"不代表"稳定能跑" | 诊断结论不可复现，团队无法信任 |
| **黑盒化** | 模型升级、Prompt 微调、Agent 配置变化都可能导致行为漂移 | 改了 Agent prompt 后旧场景悄悄变差 |
| **错误级联放大** | 诊断涉及 15+ 步 Agent 调用，前序步骤偏差逐级放大 | 分类定界错误 → 信息采集方向错误 → 根因分析完全偏离 |

没有测评会导致：
- **主观性强**：依赖"感觉诊断变好了"的直觉，缺乏量化依据
- **悄悄退化**：改了 Agent 配置或升级模型后，旧 Issue 诊断变差却无人知晓
- **人工验证成本高**：Issue 越多、Agent 迭代越快，靠人肉回归成本指数级增长
- **模型不敢升级**：新模型发布时没有对比数据支撑切换决策
- **过程易忽略**：最终诊断报告可能碰巧正确但推理路径是错的

### 1.2 核心理念

```
Eval（评估）= Issue 输入 → 诊断工作流执行 → 捕获执行过程（Trace + 产物） → 一组检查规则 → 可对比的分数
```

测评的目标是建立一个**可重复、可量化、可持续演进**的评估闭环：每次 Agent/Skill 变更都能快速跑出一个可比较的分数，用数据代替直觉，用全量代替抽查。

## 2. 测评框架：谁来评？评什么？

### 2.1 三类评委：谁来打分？

诊断工作流的输出既有可程序化验证的硬指标（代码仓是否 clone 成功、报告文件是否存在），也有只能靠语义理解才能判断的软指标（根因分析合理性、修复建议质量）。单一评分手段无法兼顾，必须三类组合：

```
        ┌──────────────────────────────────┐
        │         确定性评分器               │
        │   （脚本 / 断言 / 文件检查）       │
        │   快、便宜、客观、可复现            │
        │   ⇨ 负责所有"能用代码判断"的事       │
        └──────────────────────────────────┘
                        ↑
                        │ 日常主力
                        │
        ┌──────────────────────────────────┐
        │         模型评分器（Rubric）       │
        │   （LLM-as-Judge + Prompt + Schema）│
        │   灵活、可扩展、处理开放式输出       │
        │   ⇨ 负责"代码搞不定但能结构化描述"  │
        └──────────────────────────────────┘
                        ↑
                        │ 扩展能力
                        │
        ┌──────────────────────────────────┐
        │         人工评分器（专家）          │
        │   昂贵、慢、黄金标准                │
        │   ⇨ 负责"校准、诊断、兜底"          │
        └──────────────────────────────────┘
```

#### 三类评委职责对照

| 维度 | 确定性评分器 | Rubric 评分器 | 人工评分器 |
|------|------------|-------------|----------|
| **谁来评** | 脚本（Bash/Python） | 大模型（固定版本） | 鸿蒙框架领域专家 |
| **成本** | 毫秒级 / 免费 | 秒级 / API 费用 | 分钟–小时级 / 人力 |
| **稳定性** | 100% | 有抖动（需降噪） | 取决于专家水平 |
| **覆盖能力** | 已知硬指标 | 未知软指标 | 主观 + 边缘场景 |
| **典型用例** | 代码仓 clone 成功、报告文件存在、JSON 格式正确 | 根因分析合理性、修复建议质量、排查思路清晰度 | 校准 LLM、诊断 0%/100% 异常、红队测试 |
| **门禁角色** | 硬门禁 | 分级门禁（error 硬、warning 软） | 不进门禁，做采样审查 |

**选择优先级**：确定性评分器 > Rubric 评分器 > 人工评分器——能用代码判断的绝不用模型，必要时用模型，人工用于校准。

#### 确定性评分器示例

```yaml
expected_behavior:
  # 过程检查：是否调用了正确的 Agent
  - agent_called: "diagnosis-classifier"
  - agent_called: "diagnosis-root-cause-analyzer"
  # 结果检查：诊断报告是否存在
  - file_exists:
      - "outputs/诊断报告.md"
  # 结果检查：报告是否包含关键章节
  - response_contains:
      - "根因结论"
      - "修复建议"
      - "环境信息"
  # 效率检查：工具调用次数上限
  - max_tool_calls: 20
  # 效率检查：诊断耗时上限
  - max_duration_seconds: 1800
```

#### Rubric 评分器示例

```yaml
rubric:
  observation_points:
    - 根因分析是否基于实际代码/日志证据而非凭空推断
    - 推理过程是否清晰连贯，证据链完整
    - 修复建议是否具体可执行（指明文件、行号、变更内容）
    - 是否存在幻觉或编造不存在的 API/字段
    - 兜底诊断（如触发）的排查思路是否可执行
  scoring:
    process_score: 0-100    # 过程分
    result_score: 0-100     # 结果分
    is_false_positive: bool  # 是否虚假成功（结果对但过程错）
```

### 2.2 五个维度：评什么？

```
┌─────────────────────────────────────────────────────┐
│  1. 功能正确性（Functional Correctness）—— 诊断对了吗 │
│  2. 过程质量（Process Quality）—— 诊断过程合理吗      │
│  3. 效率与成本（Efficiency & Cost）—— 划算吗          │
│  4. 鲁棒性与安全（Robustness & Safety）—— 靠谱吗      │
│  5. 体验与对齐（Experience & Alignment）—— 好用吗     │
└─────────────────────────────────────────────────────┘
```

| 大类 | 子维度 | 主要评分器 | 优先级 |
|------|--------|----------|--------|
| 1. 功能正确性 | 根因准确率、分类准确率、层面定界准确率、修复建议可用率 | 代码 | P0 |
| 2. 过程质量 | 推理合理性、步骤最优性、证据链完整性、兜底诊断可执行性 | Rubric + 人工 | P1 |
| 3. 效率与成本 | Token 消耗、Agent 调用次数、端到端延迟、失败重试率 | 代码 | P1 |
| 4. 鲁棒性与安全 | 一致性（pass^k）、异常恢复、幻觉率、越权风险 | 代码 + 人工 | P0 |
| 5. 体验与对齐 | 报告清晰度、排查思路可执行性、知识沉淀质量 | Rubric + 人工 | P2 |

#### 大类 1：功能正确性 — "诊断做对了吗？"

| 子维度 | 说明 | 评测方法 | 指标 |
|--------|------|---------|------|
| **根因准确率** | 根因结论是否与 ground truth 一致 | 与人工专家诊断结果对比 | 正确数 / 总数 |
| **分类准确率** | 问题类型分类是否正确 | 与人工标注对比 | 正确数 / 总数 |
| **层面定界准确率** | 问题层面判断是否正确 | 与人工标注对比 | 正确数 / 总数 |
| **修复建议可用率** | 修复建议是否可执行且有效 | 人工评估 + 代码验证 | 可用数 / 总数 |
| **报告完整性** | 报告是否包含所有必要章节 | JSON Schema / 关键词检查 | 完整率 % |

> P0，必须自动化、全覆盖。对应确定性评分器主战场。

#### 大类 2：过程质量 — "诊断过程合理吗？"

| 子维度 | 说明 | 评测方法 | 指标 |
|--------|------|---------|------|
| **推理合理性** | 根因分析思维链是否自洽、无跳步 | Rubric 评委 | 合理性评分 1–5 |
| **步骤最优性** | 是否走了不必要的弯路 | 比较实际步数 vs 参考解法 | 步数比 |
| **证据链完整性** | 输出是否覆盖了诊断所需的所有关键证据 | Rubric 按要点核查 | 要点覆盖率 % |
| **兜底诊断可执行性** | 兜底报告的排查思路是否可操作 | Rubric + 人工 | 可执行评分 |

> P1，最能体现"智能"水平，Rubric 评委主战场。

#### 大类 3：效率与成本 — "诊断划得来吗？"

| 子维度 | 说明 | 评测方法 | 指标 |
|--------|------|---------|------|
| **Token 消耗** | 输入 + 输出 token 总量 | API 统计 | avg / p95 tokens |
| **Agent 调用次数** | 完成诊断的 Agent 调用总数 | Trace 统计 | avg / p95 calls |
| **端到端延迟** | 从 Issue 输入到诊断报告输出 | 时间戳 | p50 / p95 latency |
| **失败重试率** | Agent 调用的重试次数 | Trace 统计 | 重试率 % |
| **单次诊断成本** | 折算成费用 | Token × 单价 | ¥/diagnosis |

> P1，一个根因准确率高但 token 花 10 倍的方案，在生产上不可接受。

#### 大类 4：鲁棒性与安全 — "关键时刻会翻车吗？"

| 子维度 | 说明 | 评测方法 | 指标 |
|--------|------|---------|------|
| **一致性/稳定性** | 相同 Issue 多次诊断结果是否一致 | 多次试验（k=5） | pass^k |
| **异常恢复** | Agent 失败、超时时能否兜底 | 故障注入测试 | 恢复成功率 |
| **幻觉率** | 是否编造不存在的 API/字段/PR | 事实核查 | 幻觉率 % |
| **越权风险** | 是否执行了超出授权的操作 | 权限断言 | 越权次数 |

> P0，诊断结论直接影响修复决策，一次错误可能导致错误修复上线。

#### 大类 5：体验与对齐 — "用户愿意继续用它吗？"

| 子维度 | 说明 | 评测方法 | 指标 |
|--------|------|---------|------|
| **报告清晰度** | 结构是否清楚、有无废话 | Rubric + 人工 | 清晰度评分 |
| **排查思路可执行性** | 兜底诊断的步骤是否具体可操作 | Rubric | 可执行率 % |
| **知识沉淀质量** | 沉淀的根因模式是否准确 | 人工抽查 | 质量评分 |

> P2，早期用 Rubric + 人工抽样，成熟后引入线上反馈闭环。

### 2.3 诊断工作流的测评侧重

诊断工作流属于「问题定位」类型 Agent，核心风险是**根因误判**和**过程偏离**：

| 侧重维度 | 核心风险 | 测评重点 |
|---------|---------|---------|
| **根因准确性** | 定位到错误的根因 → 错误修复 → 引入新问题 | 根因结论是否与人工专家一致 |
| **推理链路** | 过程跳步或逻辑断裂 → 结论碰巧正确但不可复现 | 推理过程是否逻辑清晰、证据链完整 |
| **兜底质量** | 根因无法确定时兜底报告不可执行 → 用户仍无从下手 | 兜底排查思路是否具体可操作 |
| **效率** | 诊断耗时过长 → 用户等待不耐烦 | 端到端延迟是否在可接受范围 |

## 3. 测评实施：怎么做？

### 3.1 设计测评用例集

用例集从 **触发 → 核心逻辑 → 产物质量 → 异常容错** 四个场景层层递进：

```
用例设计四大场景
┌─────────────┐   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  ① 触发      │ → │  ② 核心逻辑  │ → │  ③ 产物质量  │ → │  ④ 异常容错  │
│  该诊断吗？  │   │  过程对吗？  │   │  报告好吗？  │   │  出错扛得住？│
└─────────────┘   └─────────────┘   └─────────────┘   └─────────────┘
```

#### 场景一：触发条件用例

验证工作流是否在正确的场景被触发/不被触发。

| 用例 ID | 类型 | 输入 | 预期 | 说明 |
|---------|------|------|------|------|
| trigger-pos-01 | 正向 | `https://gitcode.com/.../issues/1`（Flutter-OHOS 图片加载异常） | 工作流启动 | 标准 Issue 链接 |
| trigger-pos-02 | 正向 | `https://github.com/.../issues/123`（Crash 问题） | 工作流启动 | GitHub Issue |
| trigger-neg-01 | 负向 | "Flutter 鸿蒙怎么用？" | 工作流不启动 | 通用问答，非 Issue 诊断 |
| trigger-neg-02 | 负向 | `https://gitcode.com/.../pulls/1` | 工作流不启动 | PR 链接非 Issue |

#### 场景二：核心逻辑用例（用例量最大）

验证诊断工作流的执行过程是否按预期步骤进行——各 Agent 是否按序执行、工具调用是否正确。

**设计方法：三步法**

第一步：梳理分支流程图 — 画出诊断工作流的所有核心分支路径

第二步：每条分支至少 1 个用例

| 分支路径 | 用例 ID | 输入 | 预期 |
|---------|---------|------|------|
| 稳定性-Crash | logic-crash-01 | 应用启动闪退的 Issue | 分类为 stability，定位到引擎层 |
| 渲染-黑屏 | logic-render-01 | 切后台切前台黑屏的 Issue | 分类为 rendering，定位到 XComponent |
| 功能-插件 | logic-func-01 | MissingPluginException 的 Issue | 分类为 functional，定位到插件层 |
| 根因-高置信度 | logic-high-conf-01 | 有明确堆栈的 Issue | 根因置信度 ≥ 0.8，进入修复建议 |
| 根因-低置信度 | logic-low-conf-01 | 信息不足的 Issue | 置信度 < 0.3，触发兜底诊断 |
| 兜底-排查思路 | logic-fallback-01 | 无法复现的偶现问题 | 兜底报告包含可执行的验证步骤 |
| 负向-过程异常 | logic-neg-01 | 标准 Issue | 不调用无关工具、无无效重试循环 |

第三步：补充组合和边界 — 多问题类型组合、阈值边缘（置信度 0.3/0.5 临界值）

#### 场景三：产物质量用例

验证诊断报告是否完整、准确、可用。

| 用例 ID | 类型 | 输入 | 检查规则 | 说明 |
|---------|------|------|---------|------|
| output-pos-01 | 正向 | 图片加载异常 Issue | file_exists + response_contains + response_format_check | 报告文件存在、关键章节完整 |
| output-pos-02 | 正向 | Crash Issue | report_has_root_cause + report_has_fix_suggestion | 包含根因结论和修复建议 |
| output-neg-01 | 负向 | 标准 Issue | response_not_contains: "编造的API" | 不编造不存在的 API（幻觉） |

#### 场景四：异常容错用例

验证异常输入、边界条件、环境故障下能否合理处理。

| 用例 ID | 类型 | 输入 | 预期 | 说明 |
|---------|------|------|------|------|
| 异常输入 | error-input-01 | 不存在的 Issue 链接 | 告知"Issue 不存在"，不编造诊断 | ID 无效时明确提示 |
| 异常输入 | error-input-02 | 非法 URL 格式 | 提示格式错误 | 输入校验 |
| 边界条件 | error-boundary-01 | 信息极少的 Issue（仅标题） | 输出兜底诊断，不崩溃 | 信息不足时兜底 |
| 环境故障 | error-env-01 | 标准请求 + 代码仓 clone 失败 | 标记 skipped，继续诊断 | 工具故障兜底 |
| 环境故障 | error-env-02 | 标准请求 + 模型 API 超时 | 自动重试，不无限循环 | API 故障兜底 |

### 3.2 设计评分规则

#### 评分规则

- 评分按**负分制**进行计算，初始总分 100 分
- 每有一个不符合预期的轨迹或结果，扣除对应的分数，扣至 0 分
- 达标标准为 **80 分**，低于 80 分认为本次诊断不通过

#### 评分维度与计分项

| 维度 | 计分项 | 说明 | 扣分 |
|------|--------|------|------|
| **结果** | 诊断结果 | 根因结论与 ground truth 不符 | -100 |
| **过程** | Agent 步骤遵循性 | 是否按预设工作流执行，每步不符 | -10/步 |
| **过程** | 步骤输出结果 | 中间步骤输出是否与预期一致，每步不符 | -10/步 |
| **过程** | Agent 调用正确性 | 是否调用了正确的 Agent，每项不符 | -10/项 |
| **效率** | 诊断耗时 | 基准 30 分钟，每超 5 分钟 | -10 |
| **效率** | Token 消耗 | 超基线 50% 以上，每超 10% | -5 |
| **稳定性** | 一致性 | N 次试验（N=5），任一不达标 | 0 分 |

#### 评分输出

每执行一个用例，将扣分结果和原因以 JSON 输出，并渲染成 HTML 报告归档。

### 3.3 建立用例基线

#### 什么是用例基线？

用例基线是单个 Issue 执行 1 次诊断后，经人工确认的预期过程和结果的快照。

**预期过程**（Agent 应该"怎么做"）：
- 各 Agent 的调用顺序和输出
- 工具调用序列（webfetch、bash、read 等）
- 中间产物（分类结果、采集素材、根因假设）
- 完整 Trace

**预期结果**（Agent 应该"产出什么"）：
- 诊断报告（Markdown）
- 根因结论
- 修复建议
- 知识沉淀

#### 基线建立流程

```
Issue 输入 → 执行诊断工作流 1 次 → 人工审核过程和结果
                                    ↓
                              可接受？ → 否 → 调整 Agent/Skill 后重新执行
                                    ↓ 是
                              保存为该用例的基线
```

核心思路：**先跑出来，再确认，确认后就是预期。**

#### 基线在评分中的作用

| 对比类型 | 对比内容 | 退化判定 | Rubric 评判 |
|---------|---------|---------|------------|
| 过程对比 | 本次 Agent 调用序列 vs 基线 | 关键步骤缺失或顺序偏离 → 过程退化 | 思维链合理性、步骤选择是否最优 |
| 结果对比 | 本次诊断报告 vs 基线 | 关键内容缺失或结论不一致 → 结果退化 | 根因准确性、修复建议质量 |
| 效率对比 | 本次 token/步数 vs 基线 | 超出基线 50% → 效率退化 | — |

#### 基线更新时机

| 触发条件 | 操作 |
|---------|------|
| Agent/Skill 配置变更 | 重新执行 1 次，人工确认后更新基线 |
| 模型版本升级 | 重新执行 1 次并确认新基线 |
| 用例本身修改 | 重新执行 1 次并确认新基线 |
| 新增 Bad Case | 获取 Issue，执行 1 次确认后记录基线 |

### 3.4 执行测评

#### 触发时机

| 触发条件 | 触发方式 | 目的 |
|---------|---------|------|
| Agent 配置变更 | CI 自动触发 | PR 合入前回归验证 |
| 模型版本升级 | 手动触发 | 验证新模型兼容性 |
| 定期巡检 | 定时触发 | 周期性全量回归，发现潜在退化 |
| Skill 知识更新 | CI 自动触发 | 验证知识库变更未破坏诊断能力 |

### 3.5 用例集维护

#### 能力测评 vs 回归测评

| 类型 | 回答的问题 | 初始覆盖率 | 定位 | 维护策略 |
|------|----------|----------|------|---------|
| **能力测评** | "工作流能把什么 Issue 诊断好？" | 20–50% | 目标山峰 | 主动拓展、频繁迭代 |
| **回归测评** | "原有诊断能力是否还在？" | 接近 100% | 防御漂移 | 只增不减，CI 每次运行 |

生命周期转化：
```
┌──────────────┐   持续优化     ┌──────────────┐
│  能力测评     │ 通过率 = 100%  │  回归测评     │
│ （新 Issue）  │ ─────────────▶│ （已掌握能力）│
└──────────────┘                └──────────────┘
      ▲                                │
      │    发现新失败模式（来自线上）     │
      └────────────────────────────────┘
```

## 4. 工程落地：如何自动化？

### 4.1 前置依赖：Trace 输出能力

ACEHarness 天然支持结构化 Trace 输出：

| 要求 | ACEHarness 实现 |
|------|----------------|
| 输出结构化 Trace | `events.jsonl` + `streams/*.chunks.jsonl` |
| Trace 内容完整 | 每步的 Agent 名称、工具调用、参数、返回值、时间戳 |
| Trace 格式稳定 | JSONL 格式，字段命名版本间一致 |

### 4.2 环境隔离

- 每次测评在独立运行目录中执行（`~/.aceharness/runs/<run-id>/`）
- 每个用例执行前清除历史运行记录和经验存储
- 测评产物（Trace、日志、报告）统一归档

### 4.3 稳定性评估

诊断工作流属于「关键决策类」Agent，**0% 容忍**（N/N 全部通过）——任何一次诊断失败都可能导致误判。

| N=5 执行结果 | 解读 | 行动 |
|-------------|------|------|
| ✓ ✓ ✓ ✓ ✓ | 全部通过 | 稳定可信赖 |
| ✓ ✓ ✓ ✓ ✗ | 存在幻觉（1/5 失败） | 不可接受，需分析失败原因 |
| ✓ ✗ ✓ ✗ ✓ | 高幻觉率（2/5 失败） | 深入排查 Agent/Skill 逻辑 |
| ✗ ✗ ✗ ✗ ✗ | 稳定失败 | 先检查用例定义或基线是否有问题 |

### 4.4 测评报告

报告应包含：

**全局概览**：
- 生成时间、用例总数
- 通过率（≥80 分的用例占比）、平均分
- 模型版本及费用区间
- 总 Token 消耗、总费用
- 平均费用 / 诊断

**用例列表**：
- 按 Issue 类型分组（稳定性/内存泄漏/功能/性能/渲染）
- 每条用例显示：名称、模型、执行次数、得分
- Trial 分数分布图（直方图）

**单用例详情**：
- Issue 链接、模型、基线耗时/Token/费用/步数
- 每次执行的明细：分数、耗时、Token、费用、各维度扣分

**稳定性评分**：
- N 次执行全部达标后取平均分
- 显示执行次数、达标标准、达标情况

## 5. 落地实践：诊断工作流测评案例

### 5.1 测评对象概述

鸿蒙跨平台框架 AI 诊断工作流部署在 ACEHarness 平台上，通过多 Agent 协作实现 Issue → 诊断报告的自动化诊断。

**调用链路**：
1. 用户输入 Issue 链接
2. 分类定界 Agent 获取 Issue 内容并分类
3. 信息采集 Agent 拉取代码仓、采集环境信息
4. 根因分析 Agent 综合分析定位根因
5. 修复建议 Agent 生成修复方案
6. 代码修改 + 验证 Agent 执行修复
7. 报告沉淀 Agent 生成诊断报告

**测评侧重**：根因准确性 + 过程合规性 + 报告质量 + 效率成本

### 5.2 测评设计

#### 评分标准

采用确定性评分 + 模型评分两层组合，满分 100 分扣分制。

**确定性评测维度**：

| 维度 | 说明 | 扣分 | 方法 |
|------|------|------|------|
| Agent 步骤 | 工作流执行流程是否与基线一致 | -10 | LCS 算法对齐基线与 Trial 的 Agent 调用步骤 |
| 效率 | 诊断耗时和 Token 消耗是否合理 | -10 | 耗时基准 30min，每超 5min 扣 5 分；Token 超基线 50% 扣 5 分 |
| 稳定性 | 同一 Issue 多次诊断，结论是否一致 | — | N=5 次执行，全部达标取平均分，任一不达标 0 分 |

**模型评分维度**：

| 维度 | 说明 | 扣分 | 方法 |
|------|------|------|------|
| 根因结论 | 根因是否与 ground truth 一致 | -80 | LLM 对比基线报告与 Trial 报告 |
| 报告章节 | 问题概述/环境信息/复现步骤/上游追踪/根因结论/修复建议/验证建议/知识沉淀 | 每项 -5，上限 -80 | LLM 逐项对比 |

**综合评分公式**：

```
单次 Trial:  trial_score = max(0, 100 + 步骤扣分 + 效率扣分 + 报告扣分)
达标判定:    trial_pass  = (trial_score ≥ 80)
用例总分:    case_score  = avg(所有 trial_score)  若全部 trial_pass = true
                        = 0                        若任一 trial_pass = false
```

#### 用例集设计

按问题类型分组，覆盖 5 大类共 30+ 个用例：

| 场景分组 | 用例数 | 覆盖内容 |
|---------|--------|---------|
| 稳定性 | 6 | Crash（启动闪退/运行时崩溃）、ANR（主线程阻塞） |
| 内存泄漏 | 5 | Widget 泄漏、原生对象泄漏、图片缓存溢出 |
| 功能 | 7 | MethodChannel 通信失败、插件缺失、权限问题、API 差异 |
| 性能 | 5 | 主线程阻塞、Widget 重建过度、启动耗时 |
| 渲染 | 5 | 黑屏（引擎未启动/路由未加载）、花屏（GPU 异常）、UI 错位 |
| 正常场景 | 3 | 全正常但需诊断确认 |
| 异常容错 | 4 | 不存在的 Issue、信息不足、代码仓 clone 失败、API 超时 |

### 5.3 基线管理

#### 基线建立流程

1. **触发诊断**：向 ACEHarness 发送 Issue 链接，启动诊断工作流
2. **获取标识**：记录本次运行的 Run ID
3. **人工审核**：在 ACEHarness 工作台查看诊断报告，确认步骤&结论正确
4. **记录基线**：将确认通过的 Run ID 写入用例配置
5. **运行时获取**：评测执行时通过 API 获取基线的完整数据（报告、步骤、耗时、Token）

#### 基线快照内容

| 数据 | 说明 |
|------|------|
| 诊断报告 | 完整的 Markdown 格式诊断报告 |
| Agent 步骤 | 各 Agent 调用流程（Agent 名 + 输出摘要 + 调用顺序） |
| 执行耗时 | 基线执行总耗时（秒） |
| Token 消耗 | 输入/输出/总 token 数 |

### 5.4 测评执行

#### 执行模式

| 模式 | 说明 | 用途 |
|------|------|------|
| 快速诊断 | 每用例跑 1 轮 | 日常开发调试、确定基线 |
| 全量测评 | 每用例跑 5 轮 | 版本验收、模型对比 |
| 按模型筛选 | 只运行指定模型 | 单模型验证 |
| 重新评分 | 对已有结果重新评分 | 评分逻辑调整后无需重新触发 |

#### 评分机制

**Agent 步骤评分**（确定性，最多扣 10 分）：
使用 LCS 算法对齐基线与 Trial 的 Agent 调用序列。步骤不一致/多余/缺少/顺序错误各扣 2 分。

**效率评分**（确定性，最多扣 10 分）：
耗时以 30 分钟为基准，每超 5 分钟扣 5 分；Token 以基线为参照，每超 50% 扣 5 分。

**报告评分**（模型评分，最多扣 80 分）：
将基线报告和 Trial 报告写入文件，调用 LLM 逐项对比。根因结论不一致直接扣 80 分；报告章节每项差异扣 5 分。

### 5.5 工程实现

#### Trace 获取

ACEHarness 通过 `events.jsonl` 和 `streams/*.chunks.jsonl` 输出完整的结构化执行轨迹：
- 工具调用事件：记录每次工具调用的名称、参数和返回结果
- Agent 输出事件：各 Agent 的分析结论和中间产物
- 时间和消耗：请求时间、完成时间、Token 消耗明细

#### 框架结构

| 层 | 职责 |
|---|------|
| API 封装层 | 封装 ACEHarness 工作流 API |
| 配置层 | 全局配置（模型/超时/评分标准）、Issue 测试集 |
| 用例定义层 | 按问题类型分组的 YAML 用例文件 |
| 采集层 | 基线数据采集器：从 ACEHarness API 获取基线报告、步骤、耗时、Token |
| 评分层 | 三个独立评分器：Agent 步骤评分、效率评分、报告评分 |
| 执行层 | 用例执行器（触发工作流、收集结果、编排评分流程） |
| 结果层 | 基线落盘、评分结果、HTML 报告 |

#### 流水线集成

- **基线确认流水线**：日常开发调试，每用例跑 1 轮，生成可视化报告
- **测评流水线**：基线确认后进入正式测评，pytest 实现，支持并发执行 + 多评分器并行
