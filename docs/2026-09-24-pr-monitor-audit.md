## 日志依据

检查 56 条历史 PR 运行记录、步骤耗时、失败原因及审批记录。旧流程中有耗时记录的步骤中位数：识别 PR 148 秒、质疑识别 163 秒、识别裁决 127 秒、检查门禁 88 秒、记录挂起 82 秒、推送质疑 205 秒、推送裁决 181 秒。部分识别、路由已在上一轮改为脚本；本轮继续清除固定判断中的模型调用。

## 问题 → 方案

1. 并发满直接丢弃事件、重复通知反复执行 → 原子落盘队列，按 PR 合并最新事件，1 秒合并窗口，忙时保留、失败退避、重启续处理；不同 PR 的读取最多并发 3 个。
2. 等待 CI 或用户的任务占满执行名额 → 只统计实际执行中的任务，启动请求预占名额，避免并发请求超额启动。
3. Webhook 漏投后一直等待 → 每 30 秒补查已开启监控的门禁。CI 仍在运行时不推进状态机，不消耗转移预算；不为未开启监控的 PR 自动创建任务。
4. 普通评论替用户回答审批 → 只允许唤醒 CI 等待；人工确认和未推送建议保持用户决策。审批正文压缩后，仍从建议产物识别等待类型。
5. 重启把无子进程的正常审批等待标为崩溃、恢复时只操作空 manager → 保留真实未回答的问题；磁盘任务通过恢复执行入口唤醒，并等待恢复状态确认。
6. 每次事件追加上下文 → 替换固定事件区块、合并待处理反馈，保留原始用户指令，控制提示词增长。
7. 固定流程仍等待模型 → 触发分流、标记就绪、人工确认记录、汇总、终止及推送核验由脚本执行。模型在第一次需要 AI 的步骤才初始化；模型服务异常不会阻塞单纯的门禁读取。
8. 推送声明不可靠 → 核对结构化推送记录的提交 SHA，同时检查本轮 `start build` 成功凭据；无记录或凭据不一致不能放行。
9. 旧 DCO 失败评论、旧关联 Issue 提示盖过当前结果；时间字符串排序受时区影响 → 当前标签/关联信息优先，按实际时间排序，非 CI 作者的 DCO 文本不作为失败信号。
10. 评论只取前 300 条、非法 JSON 被当成空检视 → 完整分页，达到保护上限显式报错；失败读取不能变成“无问题”。只读临时错误重试一次，权限错误不重试，转人工确认。
11. 门禁与检视重复拉取相同接口、DCP 明细重复下载 → 15 秒内复用同一 PR 的门禁来源快照；DCP 明细按报告及 head 缓存，单次读取限制 25 秒。PR 自身标签优先，避免同号 Issue 污染。
12. 文件工具错误也等待 20/40/60 秒 → 文件/路径错误立即进入纠正，服务拥塞保留退避；停止与跳转可在约 100 毫秒内取消重试等待。
13. 独立工作区失败后回退到共享目录 → PR 任务停止启动并报错，避免串用另一 PR 的修复文件。

监控调度放在独立 `pr-monitor-policy.ts`，保留工作区原有未提交的兼容模块改动。代码修复和修复质量评判继续使用 AI。
