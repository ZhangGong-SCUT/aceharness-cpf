# 2026-09-21 批量启动 PR 监控全军覆没——启动串行限流 + 引擎恢复退避

## 时间

2026-09-21 10:48 – 11:40（+0800）

## 解决了什么问题

### 问题

用户批量开启 ~10 个 PR 监控（31 秒内 10 个 run），**全部失败**（识别步骤即挂）。
9/20 09:11 也发生过同款批量失败。错误三连：

- `SSE failed: HTTP 503`（opencode 流式接口拒连）
- `[opencode-sdk] event stream ended before session idle`（事件流提前断开）
- `AI 服务中断：步骤未产生任何输出`

且部分 run 走 识别→终止 10 秒收场（表面 status=completed，实为快速失败）。

### 根因

两层叠加：

1. **并发突发压垮 AI 服务层**：10 个 run 同时启动，每个识别阶段 3-4 路 LLM 并发流，
   opencode serve（单进程）出现 503/流早断；当时另有 pr2081 长任务在跑（9/20 起活跃至今）加重负载。
   事后单独测试（session 创建 + 真实 prompt）完全正常；9/20 批量失败后单独重跑的 run 全部成功——确证为瞬时拥塞。
2. **引擎重试全部落在拥塞窗内**：步骤自动恢复 3 次重试**无间隔**（实测 30-60ms 连发），
   拥塞持续 2-5 分钟，密集重试只是连环烧 session。

### 方案（双层）

**AIWeb 侧（`Server/routes/prreview.js`，已重启生效）**：
- 新增启动串行队列：`startPrMonitor` 调用全局串行、最小间隔 10s；
- 校验（活跃/已合入/已关闭等 409/422）保持**即时响应**不排队；只排队真正的启动动作；
- HTTP 侧最多等 60s（前端超时 90s），超时转后台继续启动并立即返回 `queued: true`；
- 排队到点后**复查活跃 run**（防止同 PR 排队期间被前面的请求启动）。

**ACEHarness 侧（`workflow-manager.ts`，已构建、下次重启生效）**：
- 步骤自动恢复加退避：`20s × 尝试数`（20/40/60s），远低于 `STREAM_IDLE_INTERRUPT_MS`（10 分钟）
  空闲看门狗，不会误触中断；密集重试不再全部落在瞬时拥塞窗内。

### 验证结果

1. 队列算法单测 4 组全过：串行+最小间隔、任务异常不断链、超时转后台、严格提交顺序；
2. 路由快路径实测：活跃 PR 2081 → 409 即时；已合入 PR 2098 → 422（18.9s 为冷缓存拉 PR 列表的正常耗时）；
3. `node --check` / `tsc --noEmit` 通过；ACEHarness 生产构建成功；
4. 引擎改动**未重启**（pr2081 活跃 run 正在执行静态修复，重启会杀掉它）——下次重启自动生效；
   AIWeb 已重启生效，**现在可以安全批量开启监控**（排队限流自动生效）。

## 部署备注

- 引擎退避在下一次 AceHarness 重启后生效（pr2081 run 结束后任意时点重启均可）。
- opencode serve（9/6 起运行 15 天）建议在无活跃 run 时择机重启一次，进一步降低流式接口抖动概率。
