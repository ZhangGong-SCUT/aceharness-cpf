# 公网隧道守护进程超时与恢复限频修复

> 验收更正：17:36、17:38 的公网 200 只证明当时恢复。17:44 再次实测到 1033，说明此前没有完成公网入口稳定性验收；守护程序修复通过，不等于整个访问链路已经修复。后续处置及独立正式隧道的验收记录见文末。

时间：2026-10-22 17:35（Asia/Shanghai）。

分支：`cpf-ohos-issue-diagnosis`；修改前提交：`6bf2bd5`。

## 问题与现场证据

本机前端 8080、后端 3000、ACEHarness 3031 在本次排查中均可返回 200。两个公网域名曾返回 Cloudflare HTTP 530 / 错误 1033；cloudflared 日志存在到边缘节点 TCP 7844 的连接超时。连接曾恢复后再次失效，不能仅靠进程 active 或 metrics 中的连接数判断网站可用。

旧守护程序在执行 `systemctl --user restart cloudflared.service` 超过 30 秒时未捕获 `subprocess.TimeoutExpired`。现场日志明确记录：17:15:51 因此抛出异常退出，由 systemd 再拉起。重启计数与冷却只在命令返回成功后更新，失败不计数，超时退出还会清空进程内状态。

## 修复方案

- `restart_cloudflared()` 捕获命令超时及 OSError，明确记录“服务端任务可能仍在执行”，交还监控循环；命令非零退出也返回受控失败。
- 在每次重启命令执行前登记尝试，成功、失败、超时均计入 300 秒冷却和每小时最多 6 次的限额，避免故障期间连续重启。
- 冷却和小时窗口使用单调时钟，避免系统校时干扰。限额仍为当前守护进程生命周期内的计数，不宣称进程重启后仍持久化保存。
- 提取 `check_once()`，由主循环统一负责 60 秒轮询间隔；HTTP 响应使用上下文管理器关闭，并移除进程全局的 socket 默认超时副作用。

改动文件：`scripts/tunnel-watchdog.py`、`tests/test_tunnel_watchdog.py` 及本归档。没有改动其他工作区中的未提交内容，也没有修改前后端和工作流业务代码。

## 1033 复发后的补充修复（2026-10-22 19:19，Asia/Shanghai）

### 复发与定位

- 用户反馈仍打不开页面，并提供错误码 **1033**。17:44 两个公网首页均实测返回 HTTP 530 / `error code: 1033`，本机 8080、3000、3031 同期仍可返回 200；问题发生在公网隧道访问链路。
- 旧正式隧道配置强制使用 `http2`，日志存在边缘连接关闭、重连及 TCP 7844 超时。UDP/TCP 连通性预检都曾失败、随后又通过，现有证据只能确认传输不稳定，不能认定 HTTP/2 是唯一根因，也不能认定防火墙始终阻断某端口。
- 守护程序 PID `1236374` 一直存活，`NRestarts=0`，真实命令超时后仍执行冷却。此前的守护程序修复有效，但无法单独解决隧道传输不稳定。

### 实施方案与部署

1. 先启动使用现有凭据的临时 QUIC 副本，独立 metrics 端口 `20242`。17:48:49–17:48:52 注册 4 条 QUIC 连接，19:16 复查日志未见之后的重连记录。此期间并未持续执行浏览器访问测试，不把日志跨度写成连续用户访问成功时长。
2. 新增可审阅的 `scripts/cloudflared.service`，显式指定 `--protocol auto`，移除正式服务对 HTTP/2 的强制绑定。`auto` 支持先尝试 QUIC、必要时回退 HTTP/2，见 [Cloudflare 协议选择实现](https://github.com/cloudflare/cloudflared/blob/master/connection/protocol.go)。本次未注入故障测试回退分支。
3. 将该模板安装至 `~/.config/systemd/user/cloudflared.service`；现有 `~/.cloudflared/config.yml` 仅将 `protocol: http2` 改成 `protocol: auto`。保留原域名映射和凭据，未改动代理设置、网络路由、前后端或工作流业务进程。
4. 服务配置 `Restart=always`、`RestartSec=10`、`TimeoutStopSec=45`，限制停机阶段等待时间。部署前备份位于 `/tmp/cloudflared-before-auto-20261022-service` 和 `/tmp/cloudflared-before-auto-20261022-config.yml`，权限均为 0600。
5. `systemd-analyze --user verify scripts/cloudflared.service` 返回 0，安装文件与模板逐字一致。执行 daemon-reload 后重启正式隧道；19:19:11 正式进程启动，PID `1242606`，19:19:12–19:19:16 日志确认建立 4 条 **QUIC** 连接。
6. 随后停止临时 `cloudflared-quic-check.service`；复查为 `inactive/dead`、`MainPID=0`。后续公网验收仅依赖正式隧道。

预检曾显示 `suggested_protocol=http2`，但正式连接注册日志明确为 `protocol=quic`；报告采用实际连接协议，不将预检建议视作当前协议。日志还存在 UDP 接收缓冲区未达到建议值的提示；本轮没有调整系统内核参数，也没有证据证明该提示导致 1033。
