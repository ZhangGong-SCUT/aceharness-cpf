## 问题与现场证据

本机前端 8080、后端 3000、ACEHarness 3031 在本次排查中均可返回 200。两个公网域名曾返回 Cloudflare HTTP 530 / 错误 1033；cloudflared 日志存在到边缘节点 TCP 7844 的连接超时。连接曾恢复后再次失效，不能仅靠进程 active 或 metrics 中的连接数判断网站可用。

旧守护程序在执行 `systemctl --user restart cloudflared.service` 超过 30 秒时未捕获 `subprocess.TimeoutExpired`。现场日志明确记录：17:15:51 因此抛出异常退出，由 systemd 再拉起。重启计数与冷却只在命令返回成功后更新，失败不计数，超时退出还会清空进程内状态。

## 修复方案

- `restart_cloudflared()` 捕获命令超时及 OSError，明确记录“服务端任务可能仍在执行”，交还监控循环；命令非零退出也返回受控失败。
- 在每次重启命令执行前登记尝试，成功、失败、超时均计入 300 秒冷却和每小时最多 6 次的限额，避免故障期间连续重启。
- 冷却和小时窗口使用单调时钟，避免系统校时干扰。限额仍为当前守护进程生命周期内的计数，不宣称进程重启后仍持久化保存。
- 提取 `check_once()`，由主循环统一负责 60 秒轮询间隔；HTTP 响应使用上下文管理器关闭，并移除进程全局的 socket 默认超时副作用。

改动文件：`scripts/tunnel-watchdog.py`、`tests/test_tunnel_watchdog.py` 及本归档。没有改动其他工作区中的未提交内容，也没有修改前后端和工作流业务代码。

### 原因边界与此前方案的不足

1. [Cloudflare 对 1033 的说明](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1033/)是云端找不到可用的隧道连接实例。本次本机服务探活正常，多条隧道连接反复超时，并出现真实请求中断，故此次访问故障定位于公网隧道链路。
2. 上次修改消除了强制 HTTP/2，并修复守护程序自身的超时退出；**没有修复持续连接反复失效的底层原因**。本次已经证实 QUIC 也会失效，不能继续将更换协议称为根治。
3. 四条连接仍来自同一台机器、同一出口，不是四条独立网络。当前默认路由通过 Wi-Fi `Huawei-Guest`，有线接口均未连接。该事实不能证明 Wi-Fi、访客网络策略、运营商或 Cloudflare 中的某一方就是唯一根因。
4. 守护程序只检查 `https://cpf-manager.xyz/api/runs`，每 60 秒一次、连续三次失败才重启。短时断连或部分请求失败可能在下一轮恢复，因而不会触发重启；`active`、连接数非零或守护程序未重启，都不能证明所有用户请求正常。
5. 代理对比检查使用了当前进程的代理环境；守护程序进程中没有 HTTP/HTTPS/ALL_PROXY/NO_PROXY 变量，探活路径不同。此前单一路径的采样不能代表所有入口路径。
6. 本轮对四个边缘地址的 TCP 7844 探测均已进入 TLS 握手，随后因系统 CA 不信任服务端证书链而退出；这不是 cloudflared 自身的连接测试，不能据此宣布 cloudflared 证书配置有误或 7844 持续畅通。本轮未关闭正式服务的证书验证。
